================================================================================
HOW THE IN-APP AGENT WAS IMPLEMENTED
Warboard iOS — owner-only AI assistant embedded in the app
================================================================================

SHORT VERSION
-------------
It's headless Claude Code running on the server, streamed into a SwiftUI chat in
the app, with the app acting as the agent's "eyes" onto the live Torn page. The
agent has ZERO tools; it "acts" only by emitting text markers that the server
turns into human-approved, read-only page inspections and reviewable userscript
/ instruction deploys.

One line: server-side headless Claude Code with no tools, fed the live page via
prompt injection, that acts only through text markers the server intercepts.


--------------------------------------------------------------------------------
1. BACKEND = HEADLESS `claude -p`, ONE SPAWN PER TURN
--------------------------------------------------------------------------------
Each chat message spawns the Claude Code CLI on the server as a non-root service
user. Key config:

  - Auth: a long-lived OAuth token from `claude setup-token` (a personal Max
    subscription — NO API key). Stored 0600, passed via CLAUDE_CODE_OAUTH_TOKEN.
  - Model pinned with `--model claude-opus-4-8` (the setup token otherwise
    defaults to Sonnet).
  - Session continuity via `--resume <sessionId>`; the id is echoed back to the
    client and reused on the next turn.

Two spawn gotchas that each cost real debugging time:

  (a) Inheriting the server's full environment HANGS the child. The server
      itself runs inside a Claude Code session, so its env carries CLAUDECODE /
      CLAUDE_CODE_* variables. The spawned child reads those and thinks it is a
      NESTED session, and stalls. Fix: give the child a clean, minimal env
      (PATH / HOME / token / locale only).

  (b) `--bare` is a trap. It looks perfect ("skip hooks, auto-memory, CLAUDE.md
      discovery") but it swaps the auth path to an apiKeyHelper and breaks the
      OAuth login ("Not logged in - please run /login"). Config isolation is
      instead achieved by running the agent in a working directory OUTSIDE any
      git tree and pointing HOME at a scratch dir — so no CLAUDE.md / AGENTS.md /
      memory dump gets pulled into every turn. A trivial turn ends up ~2k tokens.


--------------------------------------------------------------------------------
2. ZERO TOOLS, ENFORCED AND VERIFIED
--------------------------------------------------------------------------------
The agent runs with `--permission-mode bypassPermissions` PLUS a complete
`--disallowed-tools` list naming every built-in (Read, Write, Edit, Bash, Glob,
Grep, WebFetch, ... all ~31 of them). Result: the agent has NO tools at all — it
cannot touch the filesystem, run code, or browse the web.

Two things worth knowing:
  - An allow-list does NOT restrict; you must DENY explicitly.
  - The init event's tool list is not exhaustive in docs (Glob/Grep are hidden),
    so you confirm the lockdown by reading the authoritative `tools: []` and
    `mcp_servers: []` off the init event — NOT by asking the agent, whose
    self-reports about its own tools are hallucinated.


--------------------------------------------------------------------------------
3. PAGE ACCESS IS SNAPSHOT INJECTION, NOT MCP
--------------------------------------------------------------------------------
The intuitive design — give the agent an inspect-only MCP server — DOES NOT WORK
headless. `claude -p` fires the model turn while the per-invocation stdio MCP
server is still connecting (mcp_servers: "pending"), so live MCP tools never
reach the turn (true for both Sonnet and Opus — the handshake completes, just
too late).

So instead the server captures the live page state itself and PREPENDS it to the
prompt each turn:
  - URL, page title, visible text
  - a depth-capped DOM skeleton
  - recent console errors/warnings, from an owner-only document-start capture
    hook injected into the app's web view (ring-buffers console.error/warn and
    error events into a window global the snapshot reads)


--------------------------------------------------------------------------------
4. THE AGENT "ACTS" THROUGH TEXT PROTOCOLS THE SERVER PARSES
--------------------------------------------------------------------------------
Because it has no tools, richer capabilities are implemented as MARKERS the agent
emits in its text. The server intercepts each marker, does the work, and RESUMES
the same session (--resume) with the result fed back in:

  ===INSPECT===  + a fenced JS block
      A READ-ONLY page query. It runs in the app's WKWebView — i.e. the live,
      authenticated Torn page — via an owner<->device relay. Every query is
      approved INDIVIDUALLY by the owner. (A "trust this session / auto-run"
      toggle was built and then deliberately REMOVED: it bypassed the human gate
      and became a prompt-injection exfiltration vector, since Torn forum/chat/
      profile text is attacker-influenceable and could steer the agent into a
      non-read-only query.) As defense-in-depth, a server-side regex rejects any
      JS that mutates/navigates/networks/touches storage (fetch, cookie,
      localStorage, .click(, .value=, location=, ...) BEFORE it runs. The human
      approval is the primary gate; the regex is a backstop, not a sandbox.

  ===SOURCE: <filename>===
      Read a userscript's full current source. The server reads the file
      (path-jailed) and resumes — NO approval needed, since it's the owner's own
      script. The agent is told to always read a script's real current source
      before proposing an edit.

  ===FILE: <name>===  + a fenced block
      A PROPOSED change — either a complete userscript file OR a .md standing-
      instruction file. It never appears raw in the chat; it's routed to an
      "Apply & deploy" card (with an optional file viewer). On approve, the
      server path-jails the target, runs `node --check` on scripts, writes it,
      and git commits / pushes / serves it. Standing-instruction .md files are
      saved to a data dir and injected at the top of EVERY future turn's prompt,
      so the owner can persistently steer the agent's behavior across chats.


--------------------------------------------------------------------------------
5. TRANSPORT + CLIENT
--------------------------------------------------------------------------------
Server route: POST /api/agent/message (owner-gated by JWT — a single owner player
id). It returns a Server-Sent Events stream of normalized events:
  snapshot | session | delta | thinking | proposal | inspectRequest |
  inspectResult | source | done | end | error

The sessionId from the `session` event is stored and reused for --resume. A
subtle coupling: a STALE resume id HARD-FAILS a turn (exit 1, no init), which
would brick every turn once ids persist. So the server buffers events until the
init/session event and, if a --resume run dies before init, discards the output
and silently retries WITHOUT --resume (fresh session, still answers).

iOS client (SwiftUI):
  - Reached from an owner-only sparkles toolbar button; opens as a sheet.
  - The chat view model is hoisted to the parent view so the transcript survives
    sheet dismiss/reopen.
  - An AgentChatStore persists {sessionId, messages} to App-Group UserDefaults so
    the whole conversation survives a cold app launch (otherwise every launch
    started a blank, first-message chat).
  - On appear it arms the inspect relay and disables the idle timer (keep-awake)
    so long turns don't sleep the device.
  - Message bodies render in a self-sizing, non-editable UITextView so text is
    selectable/copyable and wraps correctly; the raw ===...=== protocol blocks
    are stripped from what the user sees and shown instead as an Apply card /
    "View file" sheet.


--------------------------------------------------------------------------------
6. SECURITY POSTURE (SUMMARY)
--------------------------------------------------------------------------------
  - Owner-gated everywhere (one player id).
  - Agent has zero tools (verified off the init event, not self-report).
  - Page inspection is read-only, human-approved per query, with a server-side
    mutation/navigation/network/storage guard as a second layer.
  - Deploys are path-jailed, syntax-checked, and reviewable via an Apply card.
  - The live web view runs in the owner's authenticated session, so the design
    treats Torn page content as untrusted input (indirect prompt injection) and
    never lets the model take an unapproved action against it.
